# Freedom CQA

Локальный прототип Conversation Quality Analytics для CQA Hackathon: FastAPI, GPT-4o и HTML/CSS/JavaScript без сборки. Два контура: проверка качества и апелляция с решением супервизора.

## Запуск

Требуется Python 3.10+. Из корня проекта в PowerShell:

```powershell
.\start.ps1
```

При первом запуске скрипт создаёт `.venv` и устанавливает зависимости. Для повторной установки: `./start.ps1 -Setup`. Альтернативно:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Интерфейс: [localhost:8000](http://127.0.0.1:8000). Документация API: [/docs](http://127.0.0.1:8000/docs).

На этом компьютере `.env` и `data/dev_dataset.json` уже подготовлены из предоставленных материалов. В чистой копии сначала скопируйте `.env.example` в `.env`, заполните `OPENAI_API_KEY` и импортируйте файл организаторов:

```powershell
python scripts/import_dataset.py "C:\path\invoke.json"
```

Файл должен содержать успешный ответ `isSuccess: true`, `data.records`. Импортируйте до первого запуска. При существующем хранилище записи берутся из него; для смены группы используйте «Настройки → Загрузить диалоги». В `.env` задайте полученный от организаторов `DATASET_URL`; подпись URL не публикуется в репозитории. `group_id` меняется через настройки. Без сети доступны кэшированные диалоги и оценки; для первой загрузки аудио и новой оценки сеть нужна.

## Экономия API

- `OPENAI_MAX_CALLS=3` — общий постоянный потолок попыток, а не лимит на перезапуск. Счётчик хранится в `data/data_store.json`, резервируется **до** запроса. Не удаляйте хранилище ради сброса бюджета.
- Автоматических повторов SDK нет (`max_retries=0`). Ошибка тоже расходует попытку. На каждый ответ установлен `OPENAI_MAX_OUTPUT_TOKENS=2600`.
- Выбор диалога, поиск, просмотр, апелляции и пересчёт весов API не вызывают. Актуальная оценка возвращается из кэша. Явная кнопка повторной оценки использует `force=true` и расходует вызов.
- Изменение только весов пересчитывает актуальные оценки локально. Изменение правил, шкал, названий, состава критериев или N/A переводит предыдущие оценки в `Stale`. Их нужно запускать отдельно, по одной или ограниченным пакетом. Это осознанное ограничение для сохранения бюджета пользователя, а не автоматическая обработка всех 65 записей.
- Для полной обработки осознанно увеличьте `OPENAI_MAX_CALLS` и перезапустите сервер. Это лимит числа запросов, а не денежный лимит OpenAI.
- Интерфейс показывает токены ответов, для которых получен usage, включая отклонённые валидатором. При сетевом обрыве провайдер также мог начислить токены; локальные цифры не заменяют биллинг провайдера. В первой тестовой версии usage отклонённого EN-ответа не сохранялся, поэтому для него число токенов неизвестно.

## Интерфейс

По умолчанию включена светлая тема. Кнопка в шапке переключает светлую и тёмную темы; выбор сохраняется в браузере. На рабочих экранах используются короткие подписи. Подробные правила каждого критерия раскрываются отдельно в редакторе.

## Демонстрация за пять минут

1. Выберите диалог, язык RU/KZ/EN или канал. В роли «Руководитель» нажмите «Оценить диалог». Если тестовый бюджет исчерпан, используйте уже оценённые записи.
2. Откройте критерий: исходный вес, нормированный вес, полученные баллы, обоснование и цитата. Нажмите время: переписка прокрутится; для звонка запись загрузится и перемотается относительно первой реплики. ISO-время показывается в UTC, журнал — UTC+6.
3. Переключитесь на «Оператор», нажмите «Оспорить оценку», введите основание.
4. Вернитесь в роль «Руководитель», рассмотрите апелляцию, удовлетворите с новой оценкой/N/A либо отклоните. Итог пересчитывается сразу. ИИ-обоснование сохраняется отдельно от причины ручного решения. В журнале есть предыдущий и новый результат.
5. В редакторе измените вес и сохраните. Итоги пересчитаются без API. При изменении самого правила предыдущий результат останется виден с пометкой о необходимости переоценки. Можно добавлять и удалять критерии.

## Расчёт и валидация

Восьмикритериальный исходный чек-лист воспроизведён из `CQA_Chat_Quality_Checklist.pdf` (стр. 1–3). Базовые веса: 10, 15, 20, 20, 15, 15, 5, 0. Ступени консультации: 0/5/10/15/20; ведения диалога: 0/4/7/10. Грубые ошибки имеют нулевой вес и отдельный флаг, итог не обнуляют.

Для применимых критериев с баллами:

```text
S = сумма базовых весов применимых критериев
нормированный вес_i = вес_i / S × 100
баллы_i = значение_i / максимум_шкалы_i × нормированный вес_i
итог = round(сумма баллов_i, 2)
```

Для бинарной оценки максимум равен 1. Если `S = 0`, итог `null`. Промежуточные значения не округляются; итог считается через `Decimal` с `ROUND_HALF_UP`. Пример: 02 и 03 = N/A, 04 = 10, 06 = 7, остальные балльные критерии = Да. Тогда `S = 100 − 15 − 20 = 65`; заработано до нормирования `10 + 10 + 15 + 10.5 + 5 = 50.5`; итог `50.5 / 65 × 100 = 77.69`.

ИИ не считает арифметику. Сервер проверяет ровно один результат на критерий, разрешённые ступени, допустимость N/A, существование реплики, точное вхождение цитаты и совпадение времени. Невалидный ответ не сохраняется как оценка. Точное вхождение цитаты подтверждает источник, **но не гарантирует правильность смысловой оценки**; требуется проверка аудитором. Bot/system — контекст; системное подтверждение идентификации может быть доказательством.

Использован `response_format=json_schema` со строгой схемой вместо устаревшего JSON mode из текстового задания: [официальная документация OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs). Модель сохранена `gpt-4o`, температура 0.

## API

Чтение не требует заголовков. Для записи передавайте `X-Role: operator` или `X-Role: supervisor`. Для QA при настроенном `QA_SUPERVISOR_TOKEN` также нужен `X-Supervisor-Token`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/health` | Состояние, режим доступа и бюджет |
| GET | `/api/conversations` | Индекс, `language`, `channel`, `status`, `search` |
| GET | `/api/conversations/{id}` | Транскрипт, оценка, апелляции и история |
| GET | `/api/conversations/{id}/audio` | MP3, локальный кэш и HTTP Range |
| GET / POST | `/api/checklist` | Чек-лист; POST `{version, criteria}` с защитой от потери конкурентных правок |
| POST | `/api/evaluate/{id}?force=false` | Оценка или кэш, только QA |
| POST | `/api/evaluate-batch` | `{conversation_ids:[...]}`; без превышения оставшегося бюджета |
| POST | `/api/appeals/submit` | `{conversation_id, criterion_id, evaluation_id, comment}` |
| POST | `/api/appeals/resolve` | `{conversation_id, criterion_id, appeal_id, action, new_score, is_na, resolution_comment}` |
| GET | `/api/audit?conversation_id=...` | Журнал с предыдущими и новыми значениями, только QA |
| POST | `/api/dataset/refresh?group_id=DEV` | Загрузка группы через сервер, только QA |

`evaluation_id` и `appeal_id` дополняют минимальное задание, чтобы не применить решение к устаревшей оценке. Повторная ожидающая апелляция по критерию запрещена; повторное разрешение возвращает 409. Изменение правил помечает ожидающие апелляции `SUPERSEDED`, история сохраняется. При ожидающей апелляции принудительная переоценка заблокирована до её разрешения.

Организаторская audio_url может вести на HTML-плеер. Сервер извлекает только `audio/source src`, разрешает наблюдавшийся HTTPS-хост `freedomholdingcorporation.crm11.dynamics.com`, скачивает до 60 MB и обслуживает файл с Range. HTML/JavaScript организаторов в приложение не внедряются.

## Проверка

```powershell
python -m pytest -q
node --check frontend/app.js
```

Тесты используют фиктивный evaluator без сети и платы: формулы, N/A, ступени, нулевой знаменатель, отдельный флаг, верификация цитат, лимит/кэш, обе ветки апелляции, версии правил, роли и безопасное извлечение аудио.

Платную проверку нужно запускать явно, не более трёх ID. Скрипт использует серверный лимит и останавливается на первой ошибке:

```powershell
python scripts/live_smoke.py p4-ru-002 p1-kz-001 p1-en-001
```

Сводка сохраняется в игнорируемый `output/validation.json`; повторный запуск с актуальными оценками использует кэш.

Фактические результаты, расход трёх тестовых попыток и ограничения проверки EN описаны в [VALIDATION.md](VALIDATION.md).

## Структура и ограничения

```text
backend/main.py             API, атомарное JSON-хранилище, бюджет, апелляции, аудио
backend/scoring_engine.py   динамический чек-лист, проверка значений, расчёт
backend/ai_evaluator.py     GPT-4o, строгая схема, проверка доказательств
frontend/                  HTML, CSS, vanilla JS, плеер и редактор
tests/test_cqa.py           проверки без OpenAI
scripts/                   импорт и явная платная проверка
data/                      локальные данные, ключей нет; исключено из Git
.env                       ключ и подписанный URL; исключено из Git
```

Это прототип для локальной демонстрации, а не проверенное промышленное развёртывание. По умолчанию роли переключаются без входа; оператор не привязан к конкретному сотруднику. QA-токен защищает записи супервизора, но не является полноценной аутентификацией. Для банковской эксплуатации нужны SSO, привязка диалогов к сотрудникам, полноценный RBAC, шифрование, политика хранения, защищённый неизменяемый аудит, БД и независимая проверка качества ИИ.

Используйте **один** Uvicorn worker/процесс на файл хранилища. Потоковые блокировки и атомарная замена JSON работают внутри процесса; межпроцессная синхронизация не реализована. Журнал локальный, не защищён от изменения владельцем файлов.

HTML/CSS/JS не зависят от сборщика или внешнего CDN. Для Dynamics 365 требуется зарегистрировать web resource, настроить HTTPS API/CORS и задать `window.CQA_API_BASE` перед `app.js`; пути `/static/...` в HTML нужно заменить на пути зарегистрированных ресурсов. Интеграция в реальном Dynamics tenant в этой работе не проверялась. Ключ OpenAI остаётся на сервере.

Ни ключ, ни оригинальный датасет, ни подписанные ссылки не включаются в Git. Принудительная отправка `git push --force` из приложенного текста не выполняется.
