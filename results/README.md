# Результаты zhigitter

Формат соответствует приложению `CQA_Student_Guide_Appendix_Results.pdf` (страницы 1–3): JSON, UTF-8, `schema_version: "1.0"`.

| Файл | Исходный набор | Результаты |
|---|---|---|
| [dev/results.json](dev/results.json) | DEV | 65 записей, все `status: "ok"` |
| [prod/results.json](prod/results.json) | FBroker | 10 контрольных чатов, все `status: "ok"` |

Три диалога SWAP сохранены только в локальной системе для отдельного задания организаторов. Они не оценивались и не включены ни в одну выгрузку.

Результаты взяты из сохранённых ответов OpenAI `gpt-4o-2024-08-06`, полученных приложением. Это не ручная подстановка оценок и не ответы тестовых заглушек. При подготовке этих файлов новых API-вызовов не было. Сервер проверил актуальность правил и исходного транскрипта, допустимые значения и ссылки на доказательства; итог пересчитан программой. На момент выгрузки решений по апелляциям не было. При последующих выгрузках используются финальные значения после апелляций.

Каждый результат содержит ровно восемь критериев: `contact`, `discovery`, `identification`, `consultation`, `empathy`, `dialogue`, `closure`, `critical`. Значения — настоящие JSON boolean, числа исходных ступеней или null в разрешённых случаях. `evidence_turns` сохраняет все ссылки модели и нумерует исходный массив с 1, включая client, operator, bot и system. Грубая ошибка передаётся отдельным `critical_flag` и не обнуляет остальные баллы.

Полные переписки, аудиоссылки, ключи API и таблицы соответствий персональных данных не публикуются. Обоснования дополнительно проходят локальное скрытие обнаруженных персональных данных. Эта эвристика не гарантирует обнаружение всех имён и адресов на RU/KZ/EN. Проверка структуры и ссылок также не доказывает смысловую безошибочность оценок модели.

## Повторная выгрузка без обращения к AI

Из корня проекта, после оценки диалогов в интерфейсе:

```sh
.venv/bin/python scripts/export_results.py --team zhigitter --group dev
.venv/bin/python scripts/export_results.py --team zhigitter --group prod
```

На Windows вместо `.venv/bin/python` используйте `.\.venv\Scripts\python.exe`.

По умолчанию скрипт выбирает нужный набор из общего локального хранилища `data/data_store.json`. Для дополнительной проверки по исходному ответу организаторов можно передать `--dataset data/fbroker_20261108.json` вместе с `--group prod`. Параметр `--store` задаёт другую копию хранилища. Полный набор DEV должен содержать 65 записей, FBroker — 10. SWAP нельзя экспортировать как PROD.

Отсутствующие, устаревшие, некорректные оценки и случаи ручного разбора сохраняются как `status: "error"`, `criteria: []`, `score: null` с безопасной причиной. Они не заменяются нулём или N/A. Если есть ошибки, скрипт завершится с кодом 2. Повторная оценка выполняется отдельно через интерфейс; экспорт не запускает её автоматически.

[schema.json](schema.json) — наша реализация проверочной JSON Schema по приложению организаторов. Дополнительно проверяются точное покрытие исходных ID, уникальность критериев, границы ссылок и расчёт итоговых баллов. [run_manifest.json](run_manifest.json) фиксирует метаданные текущей выгрузки и контрольные суммы файлов.

После обновления файлов их нужно закоммитить и отправить в GitHub. Локальное сохранение само по себе не является сдачей.

Ручная разметка создана ассистентом, не организаторами; согласие с ней не измеряет точность по независимому эталону. Текущая версия правил указана в `run_manifest.json` и реализована в `backend/evaluation_policy.py`.
