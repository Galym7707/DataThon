# Результаты ZHIGITTER

Формат основан на `CQA_Student_Guide_Appendix_Results.pdf`, стр. 1–3:

- `dev/results.json` — исходные 65 DEV-диалогов (60 чатов и 5 звонков).
- `prod/results.json` — 10 контрольных чатов, после получения соответствующего набора.
- `schema.json` — локальная проверочная JSON Schema формата 1.0. Это реализация требований приложения, а не отдельная схема, опубликованная организаторами.
- `calibration/` — ручная разметка и сравнение каждого критерия до и после настройки.

Контрольный набор пока не получен. Папка `prod` оставлена без вымышленных результатов.

В экспорт входят только ID из исходного ответа API, не пользовательские диалоги, добавленные в интерфейсе. Восемь кодов критериев: `contact`, `discovery`, `identification`, `consultation`, `empathy`, `dialogue`, `closure`, `critical`. Бинарные оценки передаются как boolean, шкалы — как числа, N/A — как null. `evidence_turns` нумеруются с 1 по исходному массиву, включая бота, клиента и системные события. `critical_flag` не обнуляет итог.

Для `contact=null` реализовано разрешённое организатором исключение: DEV-звонок с отсутствующим началом записи. Для обычного чата такой экспорт запрещён. Проверка условия N/A остаётся смысловой задачей оценщика; JSON-валидатор проверяет типы, канал и структуру.

## Повторный запуск

Из корня проекта, при работающем локальном сервере и настроенном `.env`:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/evaluate_dataset.py --report output/dev_run.json
.\.venv\Scripts\python.exe -X utf8 scripts/export_results.py --team ZHIGITTER --group dev
```

Первый скрипт вызывает платную модель только для отсутствующих/устаревших оценок; `--force` явно запускает повторную оценку. Он сохраняет промежуточный отчёт после каждого диалога. Новые инструкции или смена модели делают кэш устаревшим. Ошибка оценки сохраняется как ошибка, не как нулевой балл.

Экспорт не вызывает модель. Он проверяет версию правил, подпись промпта/модели, исходный транскрипт, допустимые значения, доказательства, покрытие ID и итоговый расчёт. Отсутствующая/устаревшая оценка представляется через `status: "error"`, пустой `criteria` и `score: null`; код завершения скрипта при наличии ошибок равен 2. Готовый файл проходит проверку `schema.json` и дополнительные проверки по исходному набору.

Для PROD сначала получите исходный набор через API организаторов и загрузите его в приложение. Затем:

```powershell
.\.venv\Scripts\python.exe -X utf8 scripts/evaluate_dataset.py --dataset data/prod_dataset.json --report output/prod_run.json
.\.venv\Scripts\python.exe -X utf8 scripts/export_results.py --team ZHIGITTER --group prod --dataset data/prod_dataset.json
```

В DEV должно быть 65 записей, в PROD — 10. Не переносите результаты DEV в PROD и не публикуйте подписанные ссылки из исходных ответов API.

## Принятые трактовки

Базовые веса и формула сохранены. Общая инструкция не требует идентификации; новое индивидуальное ограничение конкретного счёта считается защищённой информацией. Его раскрытие без подтверждённой личности затрагивает и идентификацию, и флаг раскрытия. Последняя трактовка зафиксирована командой на основании чек-листа: в предоставленной переписке организатор не дал прямого подтверждения для этих конкретных кейсов.

Порог первой реакции в 3 минуты исключён из оценки согласно `CQA_Chat_Quality_Checklist.pdf`, стр. 2. Норматив удержания на линии не установлен согласно ответу организатора. Предупреждение об ожидании оценивается отдельно. Корректная передача вопроса на проверку может считаться следующим шагом; при этом дополнительные вопросы клиента нельзя игнорировать.

Ручная разметка выполнена ассистентом, не предоставлена организаторами. Согласие модели с ней не является измерением точности на независимом эталоне. Проверка звонков по транскрипту не подтверждает интонацию, дикцию или фактическое исполнение обещаний оператора.
